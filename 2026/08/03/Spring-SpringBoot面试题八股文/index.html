Spring 复习

一、Spring 核心

1.1 IOC（控制反转）

Q：什么是 IOC？什么是 DI？二者关系？

IOC（Inversion of Control）是一种设计思想，核心是将对象的创建和依赖关系的管理从代码中剥离，交由容器统一管理。DI（Dependency Injection）是 IOC 的具体实现方式，容器在运行时自动将依赖对象注入到组件中。

Q：BeanFactory 和 ApplicationContext 的区别？

特性 BeanFactory ApplicationContext
初始化策略 懒加载，getBean 时实例化 预加载，启动时一次性实例化所有单例
国际化 不支持 支持 MessageSource
事件发布 不支持 支持 ApplicationEvent
AOP 集成 需手动 自动集成
注解支持 @Autowired 不自动支持 支持 @Autowired、@PreDestroy 等

实际开发中几乎都用 ApplicationContext，它是 BeanFactory 的子接口，功能更丰富。

Q：Spring 容器的启动流程？

  1. 读取配置（注解/XML/JavaConfig），解析 BeanDefinition
  2. 将 BeanDefinition 注册到 BeanDefinitionRegistry
  3. 执行 BeanFactoryPostProcessor（如 ConfigurationClassPostProcessor 处理 @Configuration、@ComponentScan、@Import）
  4. 注册 BeanPostProcessor
  5. 初始化单例 Bean（按依赖顺序，涉及三级缓存解决循环依赖）
  6. 发布 ContextRefreshedEvent 事件

Q：Bean 的生命周期？

Q：@PostConstruct、InitializingBean、init-method 的执行顺序？

@PostConstruct → InitializingBean#afterPropertiesSet → init-method。

@PostConstruct 是 JSR-250 注解，由 CommonAnnotationBeanPostProcessor 处理，在 postProcessBeforeInitialization 阶段执行，早于 afterPropertiesSet。

1.2 AOP（面向切面编程）

Q：AOP 的实现原理？JDK 动态代理和 CGLIB 的区别？

对比项 JDK 动态代理 CGLIB
前提 目标类实现接口 无需接口，通过继承生成子类
原理 java.lang.reflect.Proxy + InvocationHandler ASM 字节码生成子类
性能 创建快，调用慢（反射） 创建慢，调用快（FastClass）
限制 只能代理接口方法 不能代理 final 类/final 方法

Spring Boot 2.x 起默认 spring.aop.proxy-target-class=true，即默认使用 CGLIB。

Q：@Aspect 中各注解的执行顺序（环绕、前置、后置、异常、最终）？

正常执行：@Around（前半段）→ @Before → 目标方法 → @Around（后半段）→ @AfterReturning → @After

异常执行：@Around（前半段）→ @Before → 目标方法抛异常 → @AfterThrowing → @After

@After 类似于 finally，无论正常还是异常都会执行。

Q：AOP 失效场景？

  1. 同类内部方法调用：this.method() 不经过代理对象，切面不生效。解决：注入自身代理、AopContext.currentProxy()、拆分类。
  2. final 方法/类：CGLIB 无法继承。
  3. private 方法：JDK 代理只能代理接口方法，CGLIB 对 private 方法也不生效。
  4. 非 Spring 管理的对象：new 出来的对象不在容器中，不会被代理。

1.3 事务管理

Q：@Transactional 的传播行为？

传播行为 含义
REQUIRED（默认） 有事务则加入，没有则新建
SUPPORTS 有事务则加入，没有则非事务执行
MANDATORY 必须在事务中运行，否则抛异常
REQUIRES_NEW 挂起当前事务，新建独立事务
NOT_SUPPORTED 以非事务方式执行，挂起当前事务
NEVER 以非事务方式执行，若当前有事务则抛异常
NESTED 有事务则嵌套执行（savepoint），没有则新建

Q：@Transactional 失效的常见场景？

  1. 方法非 public（Spring 默认只处理 public 方法）
  2. 同类内部调用（未经过代理）
  3. 异常被 catch 吞掉，未抛出
  4. 抛出的是非 RuntimeException 且未指定 rollbackFor
  5. 数据库引擎不支持事务（如 MySQL 的 MyISAM）
  6. 传播行为设置不当（如 NOT_SUPPORTED）

Q：@Transactional 的隔离级别？

对应数据库事务隔离级别：READ_UNCOMMITTED、READ_COMMITTED、REPEATABLE_READ（MySQL 默认）、SERIALIZABLE。设置 isolation = Isolation.DEFAULT 使用数据库默认隔离级别。

二、Spring Boot 核心

2.1 自动配置原理

Q：Spring Boot 自动配置的原理？

核心注解 @SpringBootApplication = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan

自动配置流程：

  1. @EnableAutoConfiguration 导入 AutoConfigurationImportSelector
  2. 读取 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（Spring Boot 3.x）或 META-INF/spring.factories（2.x）
  3. 结合 @Conditional 系列条件注解过滤，决定是否加载某个配置类
  4. 配置类中的 @Bean 方法注册 Bean，配合 @ConfigurationProperties 绑定 application.yml 属性

Q：@Conditional 系列注解有哪些？

注解 条件
@ConditionalOnClass classpath 中存在指定类
@ConditionalOnMissingClass classpath 中不存在指定类
@ConditionalOnBean 容器中存在指定 Bean
@ConditionalOnMissingBean 容器中不存在指定 Bean
@ConditionalOnProperty 配置属性满足指定条件
@ConditionalOnWebApplication 当前是 Web 应用

这也是为什么引入 starter 就能自动生效——classpath 有了对应的类，条件满足，自动配置生效。

Q：自定义 starter 的步骤？

  1. 创建 xxx-spring-boot-autoconfigure 模块，编写自动配置类
  2. 使用 @Configuration + @ConditionalOnClass + @EnableConfigurationProperties
  3. 在 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 中注册配置类全限定名
  4. 创建 xxx-spring-boot-starter 模块，仅依赖 autoconfigure 模块（pom 聚合）
  5. 使用时引入 starter 依赖即可

2.2 配置体系

Q：application.yml 和 application.properties 的区别？优先级？

  • 功能等价，格式不同
  • 同目录下 properties 优先级高于 yml
  • 多环境配置：application-{profile}.yml，通过 spring.profiles.active 激活
  • Spring Boot 2.4+ 推荐使用 spring.config.import 导入外部配置

Q：@ConfigurationProperties 和 @Value 的区别？

对比项 @ConfigurationProperties @Value
绑定方式 批量绑定（前缀+属性名映射） 逐个注入
类型支持 支持复杂对象（List、Map、嵌套 POJO） 基本类型和 String
校验 支持 JSR-303 @Validated 不支持
松散绑定 支持（first-name → firstName） 不支持
SpEL 不支持 支持

2.3 启动流程

Q：Spring Boot 启动流程？

  1. SpringApplication.run() 创建 SpringApplication 实例
  2. 推断应用类型（Servlet/Reactive/非 Web）
  3. 加载 ApplicationContextInitializer（从 spring.factories）
  4. 加载 ApplicationListener
  5. 执行 run() 方法：
    • 创建 Environment
    • 创建 ApplicationContext
    • 执行 Initializer 的 initialize()
    • 刷新容器（核心：Bean 的加载）
    • 执行 Runner（CommandLineRunner、ApplicationRunner）
    • 发布 ApplicationStartedEvent

三、Spring MVC

Q：Spring MVC 的请求处理流程？

前后端分离下，@ResponseBody / @RestController 走 HttpMessageConverter 直接写响应，不经过视图解析。

Q：@RequestMapping 的执行原理？URL 匹配规则？

启动时扫描所有 @RequestMapping，建立 URL → HandlerMethod 的映射关系（RequestMappingHandlerMapping）。

匹配优先级（从高到低）：

  1. 精确匹配：/user/detail
  2. 路径变量：/user/{id}
  3. 通配符：/user/**

Q：拦截器（HandlerInterceptor）和 Filter 的区别？

对比项 Filter HandlerInterceptor
规范 Servlet 规范 Spring MVC 规范
作用范围 所有请求（含静态资源） 只针对 Controller 处理的请求
使用上下文 不能使用 Spring 容器 Bean（需额外配置） 可以使用 Spring 容器中的 Bean
执行时机 Servlet 层面，最早执行 DispatcherServlet 内部，HandlerMapping 之后
典型场景 跨域、编码、XSS 过滤 登录校验、日志、权限

Q：Spring Boot 中如何做参数校验？

五、Spring Boot 实战高频

5.1 循环依赖

Q：Spring 如何解决循环依赖？

三级缓存机制（仅针对 setter 注入 / 字段注入的单例 Bean）：

缓存 作用
singletonObjects（一级） 完全初始化好的 Bean
earlySingletonObjects（二级） 提前暴露的半成品 Bean（可能已代理）
singletonFactories（三级） Bean 的 ObjectFactory，用于生成早期引用

流程：A 依赖 B，B 依赖 A

  1. 创建 A → 实例化 A → 将 A 的 ObjectFactory 放入三级缓存
  2. A 填充属性发现依赖 B → 去创建 B
  3. 创建 B → 实例化 B → B 依赖 A → 从三级缓存获取 A 的早期引用（触发代理创建）→ 放入二级缓存
  4. B 初始化完成 → 放入一级缓存
  5. A 拿到 B → A 初始化完成 → 放入一级缓存

Q：构造器注入的循环依赖能解决吗？

不能。因为实例化本身就需要依赖，无法提前暴露引用。解决：@Lazy 注解，或重构代码消除循环。

Q：为什么需要三级缓存，两级不行吗？

两级缓存可以解决大部分循环依赖，但无法处理 AOP 代理的场景。三级缓存的 ObjectFactory 确保在需要时才创建代理对象，保证注入的是代理对象而非原始对象。如果确定不需要 AOP，两级缓存就够了。

5.2 Bean 的作用域

作用域 说明
singleton（默认） 容器中只有一个实例
prototype 每次获取都创建新实例
request 每个 HTTP 请求一个实例
session 每个 HTTP Session 一个实例
application 每个 ServletContext 一个实例

注意：singleton Bean 注入 prototype Bean 时，prototype 不会每次刷新。解决：@Lookup 注解、ObjectFactory<T>、Provider<T>。

5.3 线程安全

Q：Spring 单例 Bean 是线程安全的吗？

不是。Spring 只保证实例唯一，不保证线程安全。如果 Bean 中有可变状态（成员变量），多线程访问会有并发问题。

解决方案：

  1. 避免在 Bean 中定义可变成员变量（推荐）
  2. 使用 ThreadLocal 保存线程私有状态
  3. 将作用域改为 prototype
  4. 加锁（synchronized / ReentrantLock）

Q：JPA 的 N+1 问题及解决方案？

  1. @EntityGraph 指定关联加载
  2. JOIN FETCH 在 JPQL 中显式关联查询
  3. 使用 @BatchSize 批量加载

9.1 Nacos 注册中心 & 配置中心

Q：Nacos 作为注册中心的原理？

Q：Nacos 和 Eureka 的区别？

对比项 Nacos Eureka
一致性协议 AP + CP 可切换（默认 AP，临时实例） 仅 AP（Peer 对等复制）
健康检查 TCP/HTTP/MySQL/MongoDB 多种 + 心跳 仅客户端心跳

Q：Nacos 的 AP 和 CP 模式怎么理解？

  • AP 模式（默认）：临时实例（spring.cloud.nacos.discovery.ephemeral=true），使用心跳 + Distro 协议，保证可用性，允许短暂不一致
  • CP 模式：持久化实例（ephemeral=false），使用 Raft 协议，保证强一致性，适用于 K8s DNS 等场景

Q：Nacos 作为配置中心，如何实现配置动态刷新？

原理：@RefreshScope 的 Bean 在配置变更时会被销毁并重新创建，下次访问时重新注入最新值。注意该 Bean 是懒加载的。

Q：Nacos 配置分组（Group）和命名空间（Namespace）的作用？

  • Namespace：隔离环境（dev / test / prod），不同命名空间配置完全隔离
  • Group：同一命名空间内按项目或业务分组，默认 DEFAULT_GROUP
  • DataId：具体配置文件标识，格式通常为 应用名-环境.yaml

Q：OpenFeign 常见面试题陷阱？

  1. GET 请求带 @RequestBody：Feign 默认 GET 请求不支持 Body，需用 @SpringQueryMap 或改为 POST

9.4 Sentinel 限流熔断

Q：Sentinel 的核心概念？

概念 说明
资源（Resource） 被保护的代码块，用 @SentinelResource 或 SphU.entry() 标记
规则（Rule） 流控规则、熔断规则、热点规则、授权规则、系统规则
指标（Metric） 滑动窗口统计 QPS、RT、异常数等

Q：Sentinel 的流控规则有哪些策略？

策略 说明
直接拒绝 QPS 超过阈值直接拒绝（FlowRuleException）
Warm Up（预热） 冷启动，逐渐达到阈值，避免突然流量冲击
匀速排队 漏桶算法，请求以均匀速度通过，超出等待超时则拒绝
关联限流 当关联资源 QPS 达到阈值时，限流当前资源（如写操作影响读操作）
链路限流 针对调用链路入口限流（配合 @SentinelResource(blockHandler)）

Q：Sentinel 的熔断策略（Circuit Breaker）？

策略 触发条件
慢调用比例 响应时间超过阈值的请求比例 > 设定值
异常比例 异常请求比例 > 设定值
异常数 异常请求数 > 设定值

熔断状态机：CLOSED（正常）→ OPEN（熔断，直接拒绝）→ HALF_OPEN（探测，放行一个请求）→ CLOSED（恢复）或 OPEN（继续熔断）

Q：@SentinelResource 的 blockHandler 和 fallback 区别？

Q：Sentinel 规则持久化方案？

Sentinel Dashboard 配置规则默认存内存，应用重启丢失。生产环境需持久化：

  1. Nacos 持久化（推荐）：规则存 Nacos 配置中心，Sentinel 客户端监听配置变更
  2. Zookeeper / Apollo：原理类似，通过外部配置中心推拉规则

Q：Sentinel 和 Hystrix 的区别？

对比项 Sentinel Hystrix
隔离策略 基于并发线程数或信号量 线程池隔离 / 信号量隔离
熔断策略 基于响应时间或异常比例/数量 基于异常比例
限流 内置丰富流控（QPS、热点、关联、链路） 不支持，需自行实现
控制台 提供开箱即用的 Dashboard 简单监控
规则配置 支持多种数据源动态刷新 仅通过代码或属性
维护状态 阿里巴巴活跃维护 Netflix 停止维护

灰度发布 Gateway + 自定义 Filter 按 Header 路由
配置管理 Nacos 配置中心 + @RefreshScope

Q：微服务网关的统一鉴权方案？

  1. Gateway 全局过滤器解析 JWT Token
  2. 校验 Token 合法性（签名、过期时间）
  3. 将用户信息放入请求头（X-User-Id、X-User-Role）向下游透传
  4. 下游服务通过拦截器读取 Header 获取用户上下文
  5. 内部服务间调用通过白名单放行（如 /inner/**），仅网关入口需要鉴权

十、高频手撕 / 设计题

  1. 实现一个分布式限流注解：自定义 @RateLimit + AOP + Redis 滑动窗口
  2. 设计全局幂等性方案：Token 机制 / 唯一请求 ID + Redis SETNX
  3. 实现多租户数据隔离：MyBatis 拦截器动态改写 SQL / Schema 隔离
  4. 自定义 Spring Boot Starter：参考 2.1 节步骤
  5. 设计一个异步任务编排方案：CompletableFuture + 自定义线程池
  6. 设计微服务灰度发布方案：Gateway + 自定义 Filter + 服务元数据权重路由
  7. 设计分布式事务方案：Seata AT 模式 / 本地消息表 + MQ 最终一致性

复习建议：3-5 年不仅要答出”是什么”，更要答出”为什么”和”底层怎么做”。重点掌握自动配置原理、事务失效、循环依赖、AOP 失效场景，这些是区分初级和中级的关键。Spring Cloud 部分重点理解各组件的协作关系和底层原理（如 Nacos 的 AP/CP 切换、Sentinel 的滑动窗口、Gateway 的 WebFlux 模型），面试中结合实际项目场景回答会更出彩。

高频问题 1：说说你对 Spring IOC 的理解

面试官意图：考察你是否真正理解 IOC 的设计思想，而不是只会背定义。

推荐回答：

IOC 的核心思想是把对象的创建和依赖管理从代码里抽出来，交给容器。以前我们需要 new UserService()，现在只需要 @Autowired，容器帮你把依赖注入进来。

好处有三点：解耦（类不关心依赖从哪来）、可测试（单测时方便 Mock）、统一管理（生命周期、作用域都由容器控制）。

实际项目中，我印象比较深的是有一次需要把某个 Service 的实现从 MySQL 切换到 MongoDB，因为依赖都是通过接口注入的，我只需要加一个 @ConditionalOnProperty 的配置类，切换配置就完成了，业务代码一行没改。

加分点：提到 BeanFactory vs ApplicationContext 的区别，以及 ApplicationContext 额外支持的事件、国际化等能力。

高频问题 2：@Transactional 失效你遇到过吗？怎么排查的？

面试官意图：考察你是否踩过坑，排查能力如何。

推荐回答：

遇到过，而且不止一次。最常见的几种情况我总结过：

第一种，同类内部调用。 我们有个订单服务，createOrder() 方法加了 @Transactional，但它是被同一个类的 batchCreate() 调用的。因为 Spring AOP 是基于代理的，this.createOrder() 走的是原对象而不是代理对象，事务就不生效。解决方式是把方法拆到不同的类，或者用 AopContext.currentProxy() 获取代理。

第二种，异常被 catch 了。 有个同事在 Service 里 try-catch 了所有异常打日志，但没往外抛。Spring 事务切面看不到异常，以为执行成功，就不会回滚。后来我们在 catch 里重新抛出 RuntimeException，或者在 @Transactional 里指定 rollbackFor = Exception.class。

第三种，方法不是 public 的。 Spring 默认只代理 public 方法，private 或 protected 上加 @Transactional 是无效的。

加分点：提到 @Transactional 的传播行为，比如 REQUIRES_NEW 适用于日志记录这种”无论主事务成功失败都要保存”的场景。

高频问题 3：说说 Spring Boot 自动配置的原理

面试官意图：这是 Spring Boot 最核心的面试题，考察你对框架底层是否了解。

推荐回答：

自动配置的核心入口是 @EnableAutoConfiguration，它通过 @Import(AutoConfigurationImportSelector.class) 导入一个选择器。

这个选择器会去读取 META-INF/spring.factories（2.x）或 AutoConfiguration.imports（3.x）里配置的所有自动配置类的全限定名。但不是所有都会生效，每个配置类上都有 @Conditional 系列注解，比如 @ConditionalOnClass、@ConditionalOnMissingBean 等，只有条件满足才会加载。

举个例子，我们在项目里引入了 spring-boot-starter-data-redis，classpath 里就有了 RedisOperations 这个类，RedisAutoConfiguration 上的 @ConditionalOnClass(RedisOperations.class) 条件满足，就会自动创建 RedisTemplate 和 StringRedisTemplate 的 Bean。如果我们自己又定义了一个 RedisTemplate，配置类上的 @ConditionalOnMissingBean 就不满足了，就不会覆盖我们自定义的。

我自己也写过自定义 Starter，把公司里通用的短信发送、OSS 上传封装成了 Starter，其他项目组引入依赖、配一下 yml 就能用。

高频问题 4：AOP 在你项目里怎么用的？遇到过失效吗？

面试官意图：考察实际使用经验和踩坑能力。

推荐回答：

AOP 在我们项目里用得比较多，主要有几个场景：

1. 接口耗时统计：自定义 @LogExecution 注解，用 @Around 切面记录方法执行时间，超过 500ms 的自动打 WARN 日志。上线后靠这个发现了好几个慢接口。

2. 操作日志：@OperationLog 注解标记在 Controller 方法上，切面里记录操作人、操作类型、请求参数、响应结果，异步写入数据库。

3. 数据权限：查询方法上加 @DataScope，切面里根据当前用户角色自动拼接 SQL 条件。

失效也遇到过。最典型的是同类内部调用，比如一个 Service 里 methodA() 调用 methodB()，methodB() 上有切面注解，但 methodB() 的切面就是不生效，因为 this.methodB() 没走代理。我们当时的解决方案是把 methodB() 拆到另一个 Service 类里。

高频问题 5：Spring Cloud 微服务怎么做的服务治理？

面试官意图：考察微服务实战经验，不是只停留在 Demo 层面。

推荐回答：

我们项目用的是 Spring Cloud Alibaba 技术栈，注册中心和配置中心用的 Nacos，服务间调用用 OpenFeign，网关用的 Gateway，限流熔断用的 Sentinel。

注册中心：所有服务启动时注册到 Nacos，消费者通过服务名获取实例列表。Nacos 支持 AP 和 CP 切换，我们用的是默认的 AP 模式（临时实例），因为微服务场景可用性比强一致更重要。

服务调用：用 OpenFeign 声明式调用，配合 LoadBalancer 做客户端负载均衡。有个坑是 Feign 默认不会透传 Header，我们写了个 RequestInterceptor，从 RequestContextHolder 里拿当前请求的 Token 放到 Feign 请求头里。

网关：Gateway 做统一入口，全局过滤器做 JWT 鉴权、请求日志、跨域处理。路由规则按 Path 匹配，配合 StripPrefix 去掉前缀。

限流熔断：Sentinel 保护核心接口，比如创建订单接口配了 QPS 限流 500，支付回调接口配了慢调用比例熔断。规则持久化到 Nacos，避免重启丢失。

高频问题 6：Nacos 和 Eureka 有什么区别？为什么选 Nacos？

推荐回答：

核心区别有三点：

1. 一致性协议：Eureka 只支持 AP（对等复制，允许短暂不一致），Nacos 同时支持 AP（Distro 协议，临时实例）和 CP（Raft 协议，持久化实例），可以根据场景切换。

2. 功能集成：Nacos 同时做了注册中心和配置中心，一套组件解决两个问题，而且配置变更支持动态刷新（@RefreshScope），Eureka 只能做注册中心。

3. 健康检查：Eureka 只有客户端心跳，Nacos 支持 TCP、HTTP、MySQL 等多种健康检查方式，还能自定义。

选 Nacos 的原因很简单——我们项目本来就需要配置中心，之前用的是 Apollo，后来发现 Nacos 能同时做注册和配置，维护成本更低，而且社区活跃，国内文档多。

高频问题 7：Sentinel 的限流和熔断有什么区别？

面试官意图：很多人混淆限流和熔断，考察理解深度。

推荐回答：

简单来说：限流是保护自己在流量高峰时不被打垮，熔断是保护自己在下游出问题时不被拖死。

限流控制的是”入口流量”，比如我配置订单创建接口 QPS 上限 500，超过的直接拒绝或者排队等待。我们大促前就用 Warm Up 预热模式，让流量慢慢涨上来，避免冷启动把服务打崩。

熔断控制的是”出口调用”，比如订单服务调用库存服务，如果库存服务响应变慢，Sentinel 检测到慢调用比例超过阈值（比如 50% 的请求超过 2s），就进入熔断状态，后续请求直接走 fallback，不再调用库存服务。过一段时间进入半开状态，放行一个请求去探测，如果恢复了就关闭熔断。

这两个是配合使用的。我们项目里对外暴露的接口做限流，服务间调用的 Feign 接口做熔断，形成完整的保护链路。

高频问题 8：Gateway 网关做了什么？

推荐回答：

我们的 Gateway 做了四件事：

1. 路由转发：前端统一请求 gateway.xxx.com/api/xxx，Gateway 根据 Path 匹配转发到对应微服务，同时用 StripPrefix 去掉 /api 前缀。

2. 统一鉴权：全局过滤器解析 JWT Token，校验通过后把用户 ID 和角色放到请求头里透传给下游。白名单路径（如登录、注册、Swagger）直接放行。

3. 跨域处理：通过 CorsWebFilter 统一配置，下游服务不需要重复配置。

4. 全链路日志：在 Pre Filter 里生成 TraceId 放到 Header 和 MDC 里，下游服务日志自动带上 TraceId，方便排查问题。

Gateway 基于 WebFlux，是非阻塞的，单机 QPS 能到上万，比之前的 Zuul 好很多。

高频问题 9：Spring 的循环依赖怎么解决的？

面试官意图：经典问题，考察对 Bean 生命周期的理解深度。

推荐回答：

Spring 用三级缓存解决 setter/字段注入的循环依赖。

假设 A 依赖 B，B 依赖 A：Spring 先创建 A，实例化后把 A 的 ObjectFactory 放到三级缓存。然后填充属性发现依赖 B，去创建 B。B 实例化后填充属性发现依赖 A，从三级缓存通过 ObjectFactory 拿到 A 的早期引用（如果 A 需要 AOP 代理，这里会创建代理对象），放到二级缓存。B 创建完成后，A 拿到 B 的引用，也创建完成。

为什么需要三级而不是两级？ 因为 AOP 代理的创建时机。postProcessAfterInitialization 阶段才会创建代理，但循环依赖时需要在更早的时机拿到代理对象。三级缓存的 ObjectFactory 就是延迟代理创建的——只有真正被循环依赖引用时才提前创建代理。如果确定没有 AOP，两级就够了。

构造器注入的循环依赖解决不了，因为实例化就需要依赖，没法提前暴露引用。可以用 @Lazy 或者重构代码消除循环。Spring Boot 2.6+ 默认禁止循环依赖，启动直接报错，倒逼你写好代码。

高频问题 10：你项目里怎么做分布式事务的？

面试官意图：3-5 年必问，考察微服务实战深度。

推荐回答：

我们项目里不同场景用了不同方案：

核心交易链路用 Seata AT 模式：比如创建订单需要同时扣库存、扣余额、生成订单记录。用 Seata 的 @GlobalTransactional 注解标记入口方法，Seata 会自动生成 undo_log，一阶段各分支本地事务提交并记录快照，如果全部成功就异步清理 undo_log，如果有一个失败就根据 undo_log 自动回滚。好处是对业务代码无侵入，缺点是全局锁有一定性能开销。

非核心场景用本地消息表 + MQ 最终一致性：比如支付成功后发积分。支付服务处理完写一条本地消息到 payment_success_msg 表，定时任务扫表发到 RocketMQ，积分服务消费消息增加积分。如果消费失败会重试，配合幂等表保证不重复加积分。这种方案性能好，但需要处理消息丢失和重复消费的问题。

技巧 说明
先说结论，再展开 不要上来就背定义，先一句话概括核心，再分点展开
结合实际项目 每个问题尽量带一句”我们项目里是这么做的…”，比纯背书强 10 倍
主动引导 回答时提到你擅长的方向，比如”这个问题让我想到我们做的限流方案…”
承认不知道 真不会就说”这块我了解不深，但我的理解是…”，不要硬编
数据说话 尽量用数字：QPS 从 X 到 Y，延迟从 Xms 降到 Yms，比形容词有说服力
分层回答 “这个问题我从三个层面来说：第一…第二…第三…”，逻辑清晰
准备追问 每个知识点想好 2-3 层追问的答案，面试官会顺着往下挖
